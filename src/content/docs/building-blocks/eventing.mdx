The Eventing block is the runtime side of the kit's integration-event story. It ships two `IEventBus` implementations - `InMemoryEventBus` (awaited, in-process) and `RabbitMqEventBus` (durable, cross-service) - an EF Core-backed outbox store for transactional delivery, an inbox store for receiver-side idempotency, a `JsonEventSerializer`, and the auto-discovery hook that registers every `IIntegrationEventHandler<TEvent>` in your module assemblies.

<Callout type="note" title="Proposed dispatch contract, not a released feature">
  The resolved-tenant dispatch contract below describes [backend commit
  9e7eca14](https://github.com/HiroshiYoshino/dotnet-starter-kit/commit/9e7eca147551789f525610d12aa0c5f94913e37c).
  These documentation changes accompany the proposed backend fix; they are not a
  release announcement. Deploy the matching backend implementation before
  relying on this contract.
</Callout>

<Callout type="tip" title="Durable delivery with explicit limits">
  Outbox delivery is at-least-once. When the business write and outbox write
  share an explicit transaction, they commit together. With the in-process bus
  and Inbox enabled, a recorded completion suppresses a later delivery to that
  handler. A crash after a business write but before Inbox insertion can repeat
  the side effect; this is not distributed-transaction or exactly-once delivery.
</Callout>

## What it ships

### Extensions

- **`AddEventingCore(services, configuration)`** - called **once by the host**, not per module. Registers `JsonEventSerializer`, a no-op `IEventTenantScope` default (the Multitenancy module swaps in a Finbuckle-backed one), the `EventingDbContext` that owns the outbox/inbox tables, exactly one `IOutboxStore` / `IInboxStore` / `IOutboxWriter`, the `OutboxDispatcher`, an `IDbInitializer` for the `framework` schema, and the single-database drain defaults. Picks the `IEventBus` from `EventingOptions:Provider` (`InMemory` default, `RabbitMQ`) and adds the dispatcher hosted service when `UseHostedServiceDispatcher` is true.
- **`AddIntegrationEventHandlers(services, assemblies[])`** - scans the supplied assemblies for `IIntegrationEventHandler<TEvent>` implementations and registers them scoped in DI.

### Event bus implementations

- **`InMemoryEventBus`** - in-process. For each event it calls `IEventTenantScope.ExecuteAsync(event.TenantId, action, ct)` and creates the consumer DI scope **inside the action, after tenant resolution**. It resolves the matching handlers and Inbox, skips recorded completions, awaits each handler, then records completion. `InMemory` selects the delivery method: the EF Core Outbox/Inbox are still database tables, not memory-only storage. The resolved-tenant behavior is part of the proposed Green change above.
- **`RabbitMqEventBus`** - durable, cross-service; uses `RabbitMQ.Client` and publishes to a durable topic exchange (`EventingOptions:RabbitMQ`).

### Outbox / inbox

- **`EventingDbContext`** - the single, framework-owned context that maps `OutboxMessages` and `InboxMessages` into schema **`framework`**. It derives from `BaseDbContext`, so it follows the tenant connection: a tenant with a dedicated database gets its outbox rows in that database, beside the business data they accompany.
- **`IOutboxWriter`** (`AddAsync`) - the publish-side contract, in `Eventing.Abstractions`. **This is what a module injects**; it never touches the eventing runtime.
- **`IOutboxStore`** (`IOutboxWriter` + `ClaimBatchAsync`, `MarkAsProcessedAsync`, `MarkAsFailedAsync`, `GetDeadLetteredAsync`, `RedriveDeadLettersAsync`) + `EfCoreOutboxStore` - the dispatcher-side surface. `AddAsync` joins the caller's transaction when one is open, so the event commits or rolls back with the business write; with no transaction it commits on its own.
- **`IInboxStore`** + `EfCoreInboxStore` - dedupe table keyed by **(event id, handler name)**. A recorded success suppresses redelivery to that handler; it does not atomically commit the handler's business writes with the Inbox row.
- **`OutboxDispatcher`** - scoped service; **claims** a batch (`OutboxBatchSize`, default 100) with a lease, deserializes, publishes via `IEventBus`, marks processed. A failing row increments `RetryCount` and backs off exponentially (`NextRetryAt`); after `OutboxMaxRetries` (default 5) it's flagged `IsDead`.
- **`OutboxDispatcherHostedService`** - background loop calling the dispatcher every `OutboxDispatchIntervalSeconds` (default 10), once per **drain target** (see below).
- **`OutboxMessage`** - `Id`, `CreatedOnUtc`, `Type`, `Payload`, `TenantId`, `CorrelationId`, `ProcessedOnUtc`, `RetryCount`, `LastError`, `IsDead`, `NextRetryAt`, `ClaimedUntilUtc`, `ClaimedBy`. Implements `IGlobalEntity` (background processors must scan across tenants).
- **`InboxMessage`** - `Id` + `HandlerName` (composite key), `EventType`, `ProcessedOnUtc`, `TenantId`. Also `IGlobalEntity`.

### Serializer

- **`JsonEventSerializer`** - System.Text.Json; the outbox stores the event's type name alongside the payload so the dispatcher can rehydrate the concrete event for publishing.

## Drain targets and multi-instance safety

Because outbox rows follow the tenant connection, the dispatcher can't poll a single database. Each cycle it asks **`IEventingDrainTargetProvider`** which databases to drain and runs one pass per target inside **`IEventingDrainScope`**, which installs the tenant context *before* the scope builds its `EventingDbContext` (that context captures `TenantInfo`, and with it the connection string, at construction). BuildingBlocks defaults to a single target; the Multitenancy module replaces it with the default database plus one target per distinct **active** per-tenant connection string - tenants sharing a database collapse to one pass. An unreachable tenant database is logged and skipped, never fatal to the cycle.

`ClaimBatchAsync` leases rows with Postgres `FOR UPDATE SKIP LOCKED` in one `UPDATE … RETURNING`, so several API instances partition a batch instead of all publishing the same message. The lease is an expiry (`OutboxClaimLeaseSeconds`, default 300), so a dispatcher that dies mid-batch has its rows recovered rather than stranded. Providers without `SKIP LOCKED` fall back to an unclaimed read and log a warning that only one instance is safe.

## Source and consumer routing

The **source database** holds the Outbox row. Its drain scope is responsible for claiming the row and writing processed, retry, or dead-letter state back to that same database. A default drain explicitly installs a root context with no dedicated connection, even when its caller previously had a dedicated tenant context.

The **consumer database** is selected independently from the event's `TenantId`. In the proposed Finbuckle implementation, `ExecuteAsync` uses a short-lived scoped `EventTenantResolver` to read the full `AppTenantInfo` from the **default tenant catalog**, without tracking and with cancellation propagated. The lookup scope is disposed before the action starts. The full context, including its connection string, is installed before a new consumer scope constructs handlers, tenant-aware DbContexts, or Inbox.

| Workflow                                 | Source Outbox          | Consumer business data                                             | Framework Inbox                                                     |
| ---------------------------------------- | ---------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------- |
| Files event for dedicated tenant T       | T's dedicated DB       | Tenant-aware consumers use T's DB                                  | T's DB, `TenantId = T`                                              |
| Root operator renews dedicated tenant T  | Default DB             | Tenant-aware consumers use T's DB; Billing remains central/default | T's DB, `TenantId = T`                                              |
| Tenant S shares T's database             | Shared physical DB     | Same physical DB, but full catalog context for S                   | Shared DB, `TenantId = S`                                           |
| Global event (null/whitespace tenant ID) | The original source DB | Root/default for tenant-aware consumers                            | Default DB; a null event `TenantId` remains a null Inbox `TenantId` |

Billing's `BillingDbContext` intentionally remains central/default; it does not inherit tenant connection routing. A Billing consumer running in T's context therefore writes subscriptions and invoices to default while its framework Inbox is in T's dedicated database. Do not infer a consumer's business-table location from its Inbox location alone.

### Resolution, rejection, and restoration

- **Active known tenant:** use the catalog's full metadata, including a dedicated or shared connection, name, and plan.
- **Unknown/deleted tenant or inactive tenant:** reject before constructing handlers or Inbox. Do not silently fall back to default. If the source row is being drained, the dispatcher records failure there and retries up to its dead-letter limit.
- **Global event:** install a minimal root context (`Id`/`Identifier = root`, active, no dedicated connection). This is not a catalog lookup of root; its actual plan, name, and active flag are not loaded. Global Webhook fanout remains skipped, and the Inbox retains the event's tenant value.
- **After success, error, or cancellation:** restore the previous ambient context. The context and awaited callback stay in the same async flow; setting AsyncLocal in an awaited helper and returning a handle is not a safe substitute.

The drain provider still enumerates only default and distinct **active** dedicated connections. A database used exclusively by an inactive or deleted tenant may never be visited, so rejection does **not** guarantee eventual dead-lettering. Another active tenant sharing that database can make it drainable. Review excluded databases explicitly rather than treating absent retry activity as success.

### Compatibility and custom dispatchers

The synchronous `Begin` API and original two-argument Finbuckle constructor remain available. `Begin` preserves full ambient metadata when the ID matches, restores nested changes on disposal, and leaves context unchanged for a null/whitespace ID. Switching to a different ID synchronously retains legacy **ID-only** behavior: it does not resolve a dedicated connection and can route custom callers to default.

Use `ExecuteAsync` for asynchronous event dispatch and construct all consumer services inside its callback. The interface's default implementation wraps the existing `Begin`, so existing synchronous or no-op implementations continue to compile; the bridge alone does not provide full catalog resolution or Finbuckle's global/default policy. Review custom `IEventTenantScope` implementations and buses when upgrading. These guarantees describe the InMemory path, not a newly implemented RabbitMQ receiver.

## Delivery status and recovery

An API success, a processed Outbox row, and an HTTP Webhook delivery are different milestones. The request can commit before any consumer executes. Outbox processed means the configured bus publish completed; for InMemory, its invoked handlers completed, but Webhook fanout only creates/enqueues delivery work. It does not prove that a remote endpoint accepted an HTTP request. Enqueue errors handled by the fanout can also allow its handler to complete. Check delivery/job status separately.

If consumer success and Inbox insertion commit but updating the **source** Outbox fails, redelivery checks the **destination** Inbox and suppresses completed handlers. If the handler commits a business write and crashes **before** Inbox insertion, the handler may run again. Concurrent deliveries and nontransactional external effects also need handler-level idempotency; the Inbox key is not a distributed exactly-once guarantee.

### Upgrade and operator review

This dispatch fix adds no schema migration, new configuration, distributed transaction, or automatic repair of existing data. Apply the normal migrator process for other pending changes, but do not invent a migration for this one.

1. Deploy the matching backend implementation before relying on this contract. Verify default catalog access, dedicated/shared connections, and consumer construction order in your environment.
2. Monitor source Outbox pending, retry, lease, and dead-letter state in **each** default/dedicated database. Correlate by event ID and handler name, not just by tenant or HTTP status. Include inactive/deleted-only databases in a controlled operator audit.
3. Review historical business writes and Inbox records that may have landed in default instead of the intended tenant database. Back up affected databases. Reconcile business effects and per-handler completion records before redelivery: a completion in the old default Inbox will not suppress a handler now checking the correct dedicated Inbox. There is no generic safe SQL move/delete procedure in this change.
4. Resolve the underlying catalog/connection/handler problem, then explicitly redrive appropriate dead letters using `RedriveDeadLettersAsync` under their **source** connection. Do not reactivate a tenant merely to drain events without an operational/security decision; do not blindly replay deleted-tenant events or clear Inbox records.
5. Confirm destination business state, destination Inbox, source completion, and any separately scheduled Webhook HTTP delivery. Publish only redacted diagnostics; omit passwords, tokens, and complete connection strings.

## How modules consume Eventing

Publishing needs **no module registration at all** - the host calls `AddEventingCore` once. A module that *handles* events registers its handlers:

```csharp
public void ConfigureServices(IHostApplicationBuilder builder)
{
    builder.Services.AddHeroDbContext<TicketsDbContext>();
    builder.Services.AddIntegrationEventHandlers(typeof(TicketsModule).Assembly);
}
```

**Publish through the outbox.** Inject `IOutboxWriter` and add the event next to your business change; the dispatcher publishes it on the next cycle:

```csharp
public async ValueTask<Unit> Handle(ResolveTicketCommand cmd, CancellationToken ct)
{
    var ticket = await _db.Tickets.FindAsync([cmd.TicketId], ct).ConfigureAwait(false);
    ticket!.Resolve(cmd.ResolutionNote);
    await _db.SaveChangesAsync(ct).ConfigureAwait(false);

    await _outbox.AddAsync(new TicketResolvedIntegrationEvent(/* … */), ct).ConfigureAwait(false);
    return Unit.Value;
}
```

**Delivery is asynchronous.** On the next cycle, the InMemory bus constructs a separate consumer scope after resolving the event tenant, not inside your HTTP request. Consumer failures update the source Outbox rather than that earlier HTTP response, and no caller (or test) should assume the side effect has already happened.

Calling `IEventBus.PublishAsync` directly runs handlers immediately, in-process, but the event is neither durable nor transactional. The kit does this in exactly one place: Chat mention notifications, where the handler pushes over SignalR and a delayed badge reads as broken. Prefer the outbox everywhere else.

The `OutboxDispatcher` picks up pending rows on the next interval (or you can call `DispatchAsync` from a Hangfire job if you don't want a hosted-service loop). The receiving side declares a handler:

```csharp
public sealed class TicketResolvedNotifyHandler(/* … */)
    : IIntegrationEventHandler<TicketResolvedIntegrationEvent>
{
    public async Task HandleAsync(TicketResolvedIntegrationEvent evt, CancellationToken ct = default)
    {
        // write a notification, send an email, etc.
    }
}
```

Host registers handlers in bulk via `AddIntegrationEventHandlers` against all module marker assemblies:

```csharp
builder.Services.AddIntegrationEventHandlers(moduleAssemblies);
```

## Configuration

```jsonc
{
  "EventingOptions": {
    "Provider": "InMemory",                       // or "RabbitMQ"
    "OutboxBatchSize": 100,
    "OutboxMaxRetries": 5,
    "OutboxRetryBaseDelaySeconds": 30,            // exponential backoff after a failure
    "OutboxRetryMaxDelaySeconds": 3600,
    "OutboxClaimLeaseSeconds": 300,               // must exceed worst-case time to publish a batch
    "EnableInbox": true,
    "OutboxDispatchIntervalSeconds": 10,
    "UseHostedServiceDispatcher": true,
    "RabbitMQ": {
      "Host": "rabbitmq",
      "Port": 5672,
      "UserName": "guest",
      "Password": "guest",
      "VirtualHost": "/",
      "ExchangeName": "fsh.events",
      "QueuePrefix": "fsh",
      "UseSsl": false,
      "PublishRetryCount": 3,
      "PublishRetryDelayMs": 1000
    }
  }
}
```

Set `UseHostedServiceDispatcher = false` when you'd rather drive the dispatcher from Hangfire on a fixed schedule (more deterministic for some ops setups).

## How to extend

### Add another transport

Implement `IEventBus`; register your implementation in place of `InMemoryEventBus` / `RabbitMqEventBus`. Bus consumers don't care which one is wired.

### Add a side-channel like Outbox-to-Kafka

`OutboxDispatcher` is small and replaceable. Subclass or wrap it to publish to Kafka in addition to RabbitMQ, or to write to multiple destinations.

### Skip the outbox for cheap fire-and-forget

`IEventBus.PublishAsync` still goes straight to the bus. If an event genuinely needs latency over durability (a cache-invalidation hint, a metrics ping, a realtime badge), publish it directly - but leave a comment saying why, because the kit's default is the outbox and a reviewer will ask.

### Drain a different set of databases

Replace `IEventingDrainTargetProvider` (and `IEventingDrainScope` if the target needs more than a tenant context installed) to teach the dispatcher about databases the tenant store doesn't know - a read replica, an archive shard, a per-region cluster.

## Gotchas

- **Domain events vs integration events** are different things in the kit. Domain events fire **inside the SaveChanges interceptor** (synchronous, in-module, via Mediator). Integration events go through the outbox and `IEventBus` (asynchronous, cross-module / cross-service). Use the right one - domain events for invariants and bookkeeping inside the module, integration events for everything else.
- **Outbox dispatcher is scoped per cycle.** Each poll gets a fresh DbContext scope; a failing publish increments the row's `RetryCount` (with `LastError` recorded) and backs off before the next attempt. At `OutboxMaxRetries` the row is flagged `IsDead` - monitor it (`outbox.deadlettered`) and replay with `RedriveDeadLettersAsync`; dead rows don't retry themselves.
- **One store, owned by the framework.** `OutboxMessages`/`InboxMessages` belong to `EventingDbContext` in schema `framework`, never to a module's context. Registering a second `IOutboxStore` makes .NET DI resolve whichever one registered last **for the whole application** - the defect behind [#1349](https://github.com/fullstackhero/dotnet-starter-kit/issues/1349), where a second module publishing broke every module's outbox. `EventingRegistrationTests` guards the count.
- **`OutboxClaimLeaseSeconds` must exceed the worst-case time to publish a batch.** If a batch can outlive its lease, another instance re-claims rows still in flight and publishes them twice.
- **A background publisher must set the tenant context before `AddAsync`,** not just before the publish - with per-tenant databases the row otherwise lands in the wrong database and is drained under the wrong target.
- **Inbox dedupes per handler, by `(EventId, HandlerName)`.** A redelivered event is skipped only for handlers that already completed it; if you mint two events with the same `Id`, the second is silently dropped for every handler. Always generate a fresh `Guid` per event.
- **Background consumers need the full tenant context first.** The proposed InMemory path does this via `IEventTenantScope.ExecuteAsync` _before_ constructing its consumer scope. Tenant-aware DbContexts capture tenant information at construction; changing it afterwards cannot repair a wrong connection. `WebhookFanoutHandler` uses the bus-established context rather than replacing it with an ID-only context; standalone delivery jobs still own their context setup.
- **RabbitMQ publishing retries in-process** (`PublishRetryCount` / `PublishRetryDelayMs`), but consumers own their durability via inbox + retry semantics.
